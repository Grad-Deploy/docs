## II. 주요 결정 사항

### 1. 토큰 문제 및 이미지 업데이트 전략 확정

- GitHub Actions에서 레지스트리 푸시, Argo CD의 레포 접근, k8s 클러스터 접근에 필요한 토큰/시크릿 관리 방식을 최우선 과제로 확정함
- 이미지 태그 관리 전략(커밋 해시 활용 등)은 추가 조사 후 확정 예정임

### 2. 서비스 카테고리 방향 확정

- 사용자 페르소나 기반 접근 대신, **정적 콘텐츠 중심으로 주로 사용되는 서비스 카테고리** 기준으로 이미지 및 설정 파일을 제공하는 방향으로 결정함
- 카테고리 예시: 커뮤니티/게시판, 이커머스 등
- 카테고리별 대표 기술 스택 예시: React + Python, spring 등 프론트엔드 프레임워크 조합
- 기존 서비스를 가져온 사용자와 설정 자체를 하지 않은 사용자로 워크플로를 분기하여 제공하기로 함
- 워크플로 내 의존성 관리 포함 (package.json, lock 파일 전략 등)

### 3. 기능 항목 우선순위 확정

- 의존성 기준으로 아래와 같이 우선순위를 확정함

| 순위 | 항목 | 이유 |
|---|---|---|
| 1순위 | 토큰 문제, 이미지 업데이트 흐름(#9), 환경변수(#8) | 파이프라인 기반 인프라, 없으면 서비스 실행 불가 |
| 2순위 | 서비스 종류 분기(#4), 버전 호환성(#7) | 프레임워크마다 Dockerfile/빌드 전략이 다름 |
| 3순위 | 리소스 제약(#5), 쿠버네티스 업데이트(#6), CI/CD 갱신 확인(#2) | 운영 안정성, 1·2순위 해결 후 확장 |

- 토큰 문제 및 #9(이미지 업데이트 흐름)는 추가 조사 후 별도 설계 확정 예정이며, 나머지 항목을 4명이 분담하기로 함

| 담당 | 담당자 | 항목 | 주요 내용 |

## IV. 회의 내용

### 1. 토큰 문제 및 이미지 업데이트 흐름 논의

- GitHub Actions에서 레지스트리 푸시, Argo CD의 레포 접근, k8s 클러스터 접근 시 토큰/시크릿이 없으면 파이프라인 전체가 멈추는 문제를 확인하고 최우선 과제로 결정함

### 2. 서비스 카테고리 방향 논의

- 사용자 페르소나 기반 접근 방식 대신 정적 콘텐츠 중심 서비스 카테고리 기준으로 이미지 및 설정 파일을 제공하는 방향으로 전환함
- 커뮤니티/게시판, 이커머스 등 카테고리별 대표 기술 스택(React + Python 등)을 기준으로 Dockerfile 및 k8s 설정 파일 템플릿을 제공하기로 함
- 기존 서비스를 가져온 사용자와 설정 자체를 하지 않은 사용자로 워크플로를 분기하여 제공하기로 함

### 3. 기능 항목 우선순위 및 역할 분담 논의

- 전체 기능 항목에 대해 의존성 기준으로 우선순위를 설정하고 4명 분담안을 논의함
- 역할 분담 결과: 고민서(#4, #7), 이은성(#8), 이온(#5, #6), 이혁제(#2)로 최종 합의함
- 이미지 태그 관리 전략은 추가 조사 후 전체 공유 예정임
- 오토파일럿 기능(#3)은 1~3순위 기능이 안정화된 이후 고도화 단계에서 검토하기로 함

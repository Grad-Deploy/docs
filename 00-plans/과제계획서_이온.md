# 과제 계획서 — LMS_Alarm (LMS 마감일 추출·알림 서비스)

| 항목 | 내용 |
| --- | --- |
| 과제명 | LMS_Alarm — LMS가 알려주지 않는 마감일을 공지 본문에서 추출해 알리는 서비스 |
| 팀명 | 딸깍 |

---
해당 프로젝트는 이온의 사이드 후보 프로젝트이며, 최종 확정 프로젝트가 아님. 

## 1. 개발 동기 및 필요성

대학 LMS(Canvas 기반)에는 **"마감 임박" 알림이 존재하지 않는다.** 알림은 전부 이벤트 기반이라 무언가 생기거나 바뀔 때만 발송된다. 캘린더 연동으로 우회하려 해도 `due_at`이 null이라 iCal 피드가 비어 있고, 영상 시청 마감일은 애초에 Canvas 과제로 등록되지 않는다.

실측 결과(`docs/99-기록/API-실측결과.md`) 캘린더·planner·upcoming_events 엔드포인트는 모두 비어 있었고, 과제 목록도 전 과목 0건이었다. 즉 **실제로 남아 있는 유일한 마감일 정보는 교수가 공지 본문에 자연어로 쓴 텍스트**다.

```
[수강 마감일 — 모두 한국시간 23:59]
1주차: 9월 14일(월) — 최초 안내에 따른 유예
2주차: 9월 14일(월)
```

구조화되지 않은 이 텍스트에서 마감일을 뽑아내는 것이 본 과제가 푸는 문제다.

## 2. 과제 목표

- 공지 본문의 자연어 마감일을 **정규식 추출 + LLM 분류** 파이프라인으로 구조화한다.
- 사용자가 **근거 문장을 보고 확정**한 마감일만 알림 대상이 되도록 한다.
- D-3 / D-1 / D-0 시점에 **웹 푸시(알림) + 카카오톡(기록)** 두 채널로 발송한다.
- 분류 정확도를 **측정 가능한 형태**로 만들고(목표 0.95), 고정 픽스처로 회귀를 막는다.
- 학교 도메인을 하드코딩하지 않아 **다른 Canvas 학교로 확장 가능한 구조**를 유지한다.

### 설계 제1원칙

**추출은 자동, 확정은 사람.** 틀린 마감일을 보내는 것이 이 서비스의 유일한 치명적 실패다. 놓치는 것보다 틀리게 보내는 것이 훨씬 나쁘므로, 분류기는 확신이 없으면 `is_deadline: false`를 반환하고, 기계는 사람이 손댄 상태(`confirmed`/`rejected`/`done`)를 절대 뒤집지 않는다.

## 3. 시스템 개요

```
Canvas API 수집 → 정규식으로 날짜 후보 추출 → LLM이 "이 중 마감일은?" 분류
→ 사용자가 근거 문장 보고 확정 → D-3 / D-1 / D-0 알림 발송
```

## 4. 주요 기능

### 4.1 수집 파이프라인 (6시간 주기)

- `GET /courses?enrollment_state=active`, `GET /announcements?context_codes[]=...` 두 엔드포인트만 호출한다. 공지는 `context_codes[]`를 여러 개 넘겨 **한 번에 전 과목**을 받는다.
- `body_html → body_text` 변환 후 `sha256`으로 `content_hash`를 계산한다. HTML 변환 시 **줄바꿈 보존이 핵심**이다. `1주차: 9월 14일` / `2주차: 9월 21일`이 한 줄로 뭉개지면 분류기가 어느 날짜가 어느 주차인지 잃는다.
- **공지 수정을 잡는다.** 교수가 마감일을 미루고 공지를 수정하는 일이 실제로 일어난다. `canvas_id`는 같고 `content_hash`만 바뀌므로 이를 재처리 신호로 쓴다.
- Rate limit은 응답 헤더(`X-Rate-Limit-Remaining`)로 관리하며, 토큰별 독립 버킷이라 사용자 수가 늘어도 서로 영향이 없다.

### 4.2 마감일 추출 — 추출이 아니라 분류 문제

```
정규식  →  날짜 후보 N개 추출        (LLM 불필요, domain/candidates.py)
LLM     →  "이 중 마감일은?" 분류    (ports/classifier.py)
```

날짜 찾기는 정규식이 하고 LLM은 판단만 한다. 선택지가 좁혀져 있어 작은 모델로도 가능하고, 출력이 구조화되어 검증할 수 있다.

- **후보는 `date`로 조립하지 않는다.** "연도 모름"과 "시각 모름"을 `date` 타입은 표현할 수 없다. 모르는 값은 `None`으로만 둔다. 원문에 없는 정보를 이 단계에서 지어내지 않는 것이 원칙이다.
- **`context`에 헤더를 함께 담는다.** 항목 줄만 보면 그것이 마감인지 알 수 없다. 이 `context`가 그대로 `deadlines.evidence`가 되어 확인 화면에 표시된다.
- 후보 추출 함수는 **어떤 입력에도 예외를 던지지 않는다.** 공지 하나가 파이프라인 전체를 죽이면 안 된다.
- 해석(`resolve`)은 순수 함수로 분리한다. 시각 없음 → 23:59 KST, "자정까지" → 그날 23:59, 연도 없음 → `posted_at` 기준 추정.

### 4.3 확인 화면 — 사람의 확정

- 근거 문장(`evidence`) 원문을 그대로 보여주고 사용자가 확정 / 거절 / 수정한다.
- 확정 전에 `domain.schedule.notification_times`로 "예정 알림: D-0만" / "알림 없이 지나갑니다"를 미리 보여준다.
- `status='pending'`만 기계가 소유한다. 재처리 시 지우고 새로 넣되, 사람이 손댄 상태는 보존한다.

### 4.4 알림 발송

| 시점 | 규칙 | 근거 |
| --- | --- | --- |
| D-3 / D-1 | 마감 3일 전·1일 전 **09:00 KST** | 밤 11시에 "3일 남았습니다"는 도움이 안 된다 |
| D-0 | 마감 **6시간 전** | 23:59 마감이면 17:59. 아직 뭔가 할 수 있는 시각 |

- 이미 지난 시점도 **행은 만들고 `status='skipped'`로 둔다.** 빼버리면 "생략된 것"과 "아직 안 만든 것"을 구분할 수 없고, 15분마다 도는 작업이 매번 다시 만들려 든다.
- 여러 건이면 **묶어서 한 통으로** 보낸다. 알림 행은 건당 유지하고 발송만 묶는다. 묶음 내 순서는 시간 순(D-3 → D-1 → D-0)이다.
- **재시도하지 않는다.** D-1 알림이 6시간 늦게 가면 이미 의미가 없고, 재시도 로직은 중복 발송의 흔한 원인이다.
- ![카카오톡 알림](docs/00-plans/image.png)

### 4.5 채널이 둘인 이유

실측 결과 **카카오톡 "나에게 보내기"는 폰을 울리지 않는다.** 메시지는 도착하지만 나와의 채팅에 조용히 쌓이고 자동 읽음 처리된다(카카오 공식 답변: 메모 용도로 노티 기능을 제공하지 않음).

| 채널 | 역할 | 비고 |
| --- | --- | --- |
| 웹 푸시 (PWA) | **알림.** 폰을 울리는 쪽 | VAPID, 무료. iOS는 홈 화면 추가 필요 |
| 카카오톡 memo | **기록.** 나중에 찾아보는 쪽 | 푸시를 놓쳐도 남는다 |

한 채널이 실패해도 다른 채널은 발송된다. 알림톡·친구톡은 사업자등록번호와 심사가 필요해 학생 팀에게는 경로가 없다.

카카오 `text` 템플릿 제약(본문 200자, `link` 필수·1개)이 메시지 형식을 결정한다. 본문에 URL을 넣지 않고(200자 예산을 가장 크게 먹는다) `link`는 단건이면 과목 Canvas URL, 묶음이면 확인 화면으로 보낸다.

## 5. 시스템 설계

### 5.1 아키텍처 — 단일 프로세스 모놀리스 + 계층형 + 외부 경계에만 포트

```
web/          FastAPI 라우트, 템플릿           ← 표현
scheduler/    APScheduler 작업 정의            ← 두 번째 진입점
services/     유스케이스 조율, 트랜잭션 경계    ← 응용
domain/       순수 로직. 의존성 0              ← 핵심
ports/        인터페이스                       ← 경계
adapters/     canvas / llm / kakao / db        ← 외부
```

의존 방향은 한 방향이다. `domain`은 아무것도 import하지 않고, `services`는 `ports`만 알며, `adapters`는 `ports`를 구현할 뿐 아무도 직접 부르지 않는다. 조립은 `main.py` 한 곳에서만 한다.

**포트를 두는 이유는 아키텍처 취향이 아니라 측정 요구 때문이다.** 외부 의존성 4개(Canvas / LLM / 카카오 / PostgreSQL)를 가짜로 바꿔 끼울 수 없으면 테스트가 성립하지 않고, 정확도 0.95라는 목표를 측정할 방법 자체가 없다. 각 포트마다 **실제 구현 1개 + Fake 1개**를 반드시 같이 만들며, Fake가 없는 포트는 미완성으로 본다. `.env`의 `CLASSIFIER=fake`, `NOTIFIER=console` 하나로 네트워크 없이 전체 파이프라인이 관통되어야 한다.

동시에 완전 헥사고날/DDD는 **하지 않는다.** 도메인 규칙이 "이 날짜가 마감인가", "언제 보낼 것인가" 두 개뿐이고, 제한된 기간에 구현보다 규약 학습에 시간이 더 든다. CQRS·이벤트 소싱·마이크로서비스도 하지 않는다.

### 5.2 진입점을 둘로 분리한다

```
docker compose
├── app        uvicorn --factory app.web.app:create_app   ← 웹
└── scheduler  python -m app.scheduler                    ← 주기 작업
```

같은 이미지, 같은 코드, 다른 `CMD`. 웹 프로세스 안에 APScheduler를 넣으면 나중에 웹을 2개로 늘리는 순간 **알림이 두 번 간다.** 분리해두면 그 사고가 구조적으로 불가능하다. 안전망으로 `notifications` 테이블에 `UNIQUE(deadline_id, kind)`를 건다 — 로직은 빠뜨릴 수 있고 제약조건은 못 빠뜨린다.

### 5.3 주기 작업 4개

| 작업 | 주기 | 내용 |
| --- | --- | --- |
| `sync_canvas` | 6시간 | 계정별 공지·과제 수집. **수집만 한다** |
| `classify_pending` | 10분 | `classification_cache`에 없는 공지만 처리 |
| `dispatch_notifications` | 15분 | `plan_notifications` → `send_due_notifications` |
| `refresh_kakao` | 1일 | `refresh_expires_at - now < 7일`이면 갱신 |

**분류 큐 테이블을 두지 않는다.** `classification_cache`에 `(content_hash, model)`이 없는 것이 곧 미분류다. 별도 큐를 쓰면 sync가 `content_hash`를 갱신한 뒤 분류가 실패했을 때 다음 sync가 unchanged로 보고 그 공지는 영영 분류되지 않는다.

한 계정의 실패가 사이클 전체를 죽이지 않는다. 예외는 계정 단위로 담고 다음 계정으로 간다 — **다음 주기가 곧 재시도다.**

### 5.4 데이터 모델 요지

- `schools` — 학교 = 도메인. 하드코딩 금지의 출발점.
- `classification_cache` — **사용자와 분리된 공용 캐시.** 같은 과목을 듣는 30명이 같은 공지를 본다. `content_hash` 단위 캐시로 LLM 호출량이 사용자 수와 무관해진다(사용자 300명 기준 14,400건 → 800건). 무료 티어 API로 운영 가능한 이유다.
- `deadlines` — **사용자별.** 공지는 공용이지만 마감일은 개인의 할 일이다. 완료 체크·거절·날짜 수정이 사람마다 다르다.
- `notifications` — `UNIQUE(deadline_id, kind)`로 중복 발송을 구조적으로 차단.
- **DB는 전부 UTC(`TIMESTAMPTZ`), 표시·해석만 KST.**
- `status` / `kind` / `source_type`에 CHECK 제약을 건다. 단, **애플리케이션 정규화가 먼저다** — 분류기가 지어낸 값은 `normalize_kind()`가 `other`로 접은 뒤에 제약을 건다.

### 5.5 보안 방침

- **학교 아이디·비밀번호는 받지 않는다.** 로그인은 카카오 OAuth에 위임해 비밀번호를 갖지 않는다.
- Canvas 토큰은 쓰기 권한을 포함하므로(수동 발급 토큰은 scope를 고를 수 없다) **Fernet 암호화 후 `BYTEA` 저장**, 암호화 키는 DB 밖 환경변수 참조만. 덤프만으로는 복호화되지 않는다.
- 반납 경로를 반드시 둔다. `users` 행 삭제 시 `ON DELETE CASCADE`로 관련 테이블이 전부 따라간다.
- 세션은 서명 쿠키, `SameSite=Lax`, HTTPS에서 `Secure`. PostgreSQL 포트는 외부에 노출하지 않는다.
- **학사시스템 스크래핑 금지.** 공식 API만 사용한다.

### 5.6 경계를 문서가 아니라 테스트로 강제한다

```python
def test_domain_imports_nothing_external()   # domain/의 import를 ast로 검사
def test_no_hardcoded_school_domain()        # 학교 도메인 문자열 grep
def test_adapters_not_imported_outside_main()
```

"경계를 지켜주세요"라고 부탁하는 것과 어기면 CI가 빨개지는 것은 다르다. 후자만 실제로 지켜진다.

## 6. 검증 계획

### 6.1 반드시 통과해야 할 함정 6건

| 원문 | 정답 |
| --- | --- |
| "'종료'(**2027년 1월 2일**)는 복습용이므로 수강 마감일과 혼동하지 마세요" | `false`. 정규식은 반드시 잡는 날짜인데 마감이 아니다 — **LLM이 필요한 이유 전부** |
| "1주차: 9월 14일(월) — 최초 안내에 따른 유예" | `true` / `viewing` / 2026-09-14 23:59 |
| "9월 11일(금) 자정까지 '이름_학과'로 변경" | `true` / `submission` / 2026-09-11 23:59 |
| "09월 16일 수업 짝수 조 참석" | `class_event` → 기본 알림 제외 |
| "9월 2주차 수업 전: Chapter 1~8" | 상대 표현, 요일 불명 → `confidence` 낮게, 사용자 지정 |
| "주차별 녹화강의 수강 마감 안내가 명확하지 않아…" | 날짜 없음, 후보 0개 |

**이 6건이 실패하면 머지 금지.**

### 6.2 검증 레벨

- **순수 함수 단위 테스트**: `extract_candidates` / `resolve` / `notification_times` / `can_notify`는 네트워크도 DB도 없이 테스트된다. 정확도 측정이 도는 곳이 여기다.
- **아키텍처 테스트**: 계층 경계 위반 시 CI 실패.
- **통합 테스트**: `CLASSIFIER=fake`, `NOTIFIER=console`로 네트워크 없이 전체 파이프라인 관통.
- **정확도 측정**: 고정 픽스처 대비 분류 정확도, 목표 0.95.

| 단계 | 기간 | 주요 내용 |

| 1단계 · 경계 확정 | (작성 필요) | **ports와 Fake를 먼저 못 박는다.** 스키마보다 이것이 먼저다 |
| 2단계 · 수집 | (작성 필요) | Canvas 어댑터, HTML→텍스트, upsert, `services/sync` |
| 3단계 · 추출·분류 | (작성 필요) | 정규식 후보 추출, `resolve`, 분류 프롬프트, 캐시 |
| 4단계 · 확인 화면 | (작성 필요) | 확정/거절/수정 UI, 예정 알림 미리보기 |
| 5단계 · 알림 | (작성 필요) | 스케줄 계산, 웹 푸시, 카카오 연동, 토큰 갱신 |
| 6단계 · 배포·검증 | (작성 필요) | Oracle Cloud 배포, 정확도 측정, 문서화 |

## 8. 역할 분담

설계 문서상 **경계가 곧 분담선**이다. ports가 먼저 합의되면 서로를 기다리지 않고 병렬로 진행할 수 있다 — 수집 담당은 `FakeLmsClient`로, 프론트 담당은 `InMemoryRepository`로 각자 간다.

| 담당 | 소유 폴더 | 의존 |
| --- | --- | --- |
| A 인프라·백엔드 | `adapters/db`, `adapters/kakao`, `scheduler`, `services/dispatch` | ports |
| B 수집·추출 | `domain/`, `adapters/canvas`, `adapters/llm`, `services/sync`, `services/extract` | ports |
| C 프론트 | `web/` | services |
| D (작성 필요) | 테스트·픽스처·문서 | — |

## 9. 기대 효과

- **사용자 측면**: LMS가 구조적으로 제공하지 못하는 마감 임박 알림을 받는다. 특히 Canvas 과제로 등록되지 않는 영상 시청 마감일이 핵심 대상이다.
- **기술적 측면**: 비결정적인 LLM을 쓰면서도 정확도를 측정 가능하게 유지하는 구조(포트 + Fake + 고정 픽스처 + 아키텍처 테스트)를 실제로 구현해 검증한다.
- **확장 가능성**: 학교는 DB의 행일 뿐이므로 `canvas_base`만 추가하면 다른 Canvas 학교로 확장된다.

## 10. 향후 확장 계획 (전시회 대응)

핵심 파이프라인(수집 → 추출 → 분류 → 확정 → 알림)은 대부분 화면 뒤에서 도는 작업이라, 그대로는 전시회에서 보여줄 것이 적다. 아래 기능들은 **새로운 데이터 소스나 아키텍처 없이, 이미 만든 로직과 데이터를 다른 방식으로 노출**하는 것을 원칙으로 삼는다.

### 10.1 홈 대시보드

- 과목별로 남은 마감일 / 완료한 마감일을 한눈에 시각화한다.
- `deadlines` 테이블은 이미 사용자·과목·상태(`pending`/`confirmed`/`rejected`/`done`) 기준으로 조회 가능하므로, 새 스키마 없이 집계 쿼리만 추가하면 된다.
- 전시회에서 첫 화면 임팩트를 담당한다 — "그냥 알림 오는 앱"이 아니라 "내 학기 전체를 관리해주는 앱"으로 보이게 하는 지점.

### 10.2 캘린더 구독 (ICS 피드)

- 확정된(`confirmed`) 마감일을 `/api/calendar/<token>.ics`로 구독할 수 있게 한다. 캘린더 앱에 URL로 등록해두면 결제일이 아니라 마감일이 반복 일정으로 뜨는 구조다.
- **주의: 10.4(제약)의 "Canvas 자체 캘린더·planner API는 쓰지 않는다"는 방침과 다른 얘기다.** 이 기능은 Canvas의 빈 캘린더 API를 끌어오는 게 아니라, 우리가 이미 확정한 `deadlines` 데이터를 우리가 만든 ICS 피드로 내보내는 것이다.
- 읽기 전용 토큰으로 발급하고, 동기화 토큰과는 분리해 관리한다(토큰 하나가 캘린더 앱에 붙여넣어지고 기기 간 공유되는 특성 때문에, sync 토큰과 섞이면 위험이 커진다).

### 10.3 라이브 추출·분류 데모

- 공지 원문을 화면에 붙여넣으면 정규식이 잡은 날짜 후보가 하이라이트되고, LLM 판정 결과(`is_deadline`, `kind`, `confidence`, `reason`)가 실시간으로 표시되는 데모 화면.
- 6.1의 **함정 6건**을 그대로 시연 시나리오로 쓴다. 특히 "'종료'(2027년 1월 2일)는 복습용" 예시처럼 정규식은 잡지만 마감이 아닌 케이스를 보여주면, 이 프로젝트의 핵심 기술(추출과 분류의 분리)이 한 화면에서 설명된다.
- 새 백엔드 로직이 필요 없다. 기존 `domain/candidates.py`, `ports/classifier.py` 호출 결과를 그대로 화면에 노출하는 프론트 작업이다.

### 10.4 정확도 뱃지

- 6.2에서 측정하는 분류 정확도(고정 픽스처 기준, 목표 0.95)를 서비스 화면에 수치로 노출한다.
- "AI가 알아서 해줍니다"가 아니라 "측정된 정확도는 이만큼입니다"를 보여주는 것이 목적. 새 로직 없이 이미 돌리는 측정을 화면에 꺼내는 정도의 비용이다.

### 10.5 방문객 참여형 챌린지

- 함정 6건 중 일부를 방문객이 먼저 맞혀보고(마감일 맞다/아니다), 그다음 실제 LLM 판정을 공개하는 미니 게임.
- 10.3(라이브 데모)의 수동적 관람을 능동적 체험으로 바꾸는 확장. 프론트 UI와 기존 분류 API 호출만 있으면 되고 백엔드 추가 없음.

### 10.6 완료 확인 알림 (옵트인)

- 사용자 기기 알림 동의를 받은 경우, 마감 1시간 전에 웹 푸시로 "과제를 완료했나요?" 확인창을 띄운다. 응답은 버튼(예/아니요) 클릭만으로 서비스 워커가 처리해 앱을 열 필요가 없다 — SubSlash의 원탭 체크인(메일 버튼 클릭 → 로컬 즉시 기록) 패턴을 웹 푸시로 옮긴 것.
- `deadlines.status`에 이미 있는 `done` 값이 지금까지 도달 경로가 없었는데, 이 기능이 그 경로를 채운다. 새 상태값이나 테이블 없이 기존 스키마의 빈 흐름을 완성하는 확장이다.
- 구현 시 정해야 할 것 두 가지:
  1. `notifications.kind`에 새 종류(예: `check-in`)를 추가해야 한다. 기존 `D-3 | D-1 | D-0`과는 응답을 요구한다는 점에서 성격이 다르다.
  2. 기존 D-0(마감 6시간 전) 알림과의 관계 — 별도로 병행할지, opt-in한 사용자는 D-0을 이 체크인으로 대체할지 결정 필요. 병행하면 같은 마감에 두 번 알림이 가서 스팸처럼 느껴질 위험이 있다.
- "아니요" 응답 시 추가 조치(재알림 등)는 두지 않는다. 재시도·에스컬레이션 로직은 4.4에서 이미 배제한 원칙(재시도하지 않는다)과 같은 이유로 최소로 유지한다.

## 11. 제약 및 범위 밖

- 과거 학기는 가져올 수 없다(종료 과목이 전부 `access_restricted_by_date`).
- 캘린더·planner·upcoming_events는 구현하지 않는다(실측상 전부 비어 있음).
- 알림톡·친구톡은 사업자등록번호·심사·비즈 앱 전환이 필요해 경로가 없다.
- OAuth2 developer key는 학교 Canvas 관리자 승인이 필요해 학부 팀이 받기 어렵다. 그래서 사용자 토큰 입력 방식을 쓴다.
